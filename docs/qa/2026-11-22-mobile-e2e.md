# Mobile app QA, end to end (2026-11-22)

The development build on the Android emulator (`solacliq_play`, Android
16) against the real local API and a fresh seed. Quick forms off, so
the app's own validation was tested. Each screen was read through its
UI hierarchy (labels, sizes, positions) and screenshots; logcat and the
API log were checked after each flow.

**Result: 0 app crashes in logcat, 0 server errors (5xx), 26 issues:
1 critical, 3 high, 5 medium, 17 low.** The two `FATAL EXCEPTION`s in
logcat are Android's `uiautomator` clashing with the test tool
(`UiAutomationService already registered`), not the app.

## Issues

Severity: **Critical** blocks work or crashes; **High** loses data or
fails silently in a main flow; **Medium** wrong data shown or a bad
input reaches the server; **Low** copy, layout or accessibility polish.

### Critical

**QA-01 Proof camera crashed to Flutter's error screen.**
- Steps: installer → returned task → Retake → refuse camera and
  location → grant both → reopen camera → Android's "Turn on location
  accuracy" → Turn on.
- Expected: the camera, with a location fix.
- Actual: red screen, `Bad state: Rebuilt
  _InheritedProviderScope<TaskCubit?> using a different constructor`
  (a grey screen in a release build; the worker is stuck).
- Seen once; not reproduced on demand (plain resume, permission grant,
  close and reopen, the tab flow all worked).
- Cause in the code: `_withTask` (`lib/app/router.dart`) gives the same
  route either `BlocProvider.value` (a cubit passed as `extra`) or
  `BlocProvider(create:)`. If one rebuild uses the other form, Flutter
  throws exactly this. Fix: give the two forms different keys, or always
  use one.

### High

**QA-02 Errors are invisible in production.**
- `bootstrap.dart` sends Flutter errors only to `dart:developer`'s
  `log()`, which only DevTools reads. Nothing reached logcat during this
  run, including QA-01 and QA-03, and there's no crash reporting.
- Expected: errors in logcat at least, and reported from the field
  (Crashlytics, as Firebase is already in the app).
- Impact: field crashes and silent failures can't be seen or counted
  after launch.

**QA-03 After shooting proof from the Upload proof tab, Submit does nothing.**
- Steps: installer home → Upload proof (centre tab) → take every photo →
  the task opens → type a note → Submit again.
- Expected: submitted, "Waiting for approval".
- Actual: nothing happens; no request reaches the server (API log); the
  note typed is lost. Leaving and reopening the task submits fine.
- Cause: the camera route creates its own `TaskCubit` and hands it to
  the task screen in `_finish()` (`pushReplacement(..., extra: cubit)`);
  the camera route then closes it, and the task screen holds a closed
  cubit whose errors are swallowed (QA-02).

**QA-04 The admin website isn't built.**
- The org admin's app screen sends them to solacliq.markcliq.com. With
  the app live and no website, nobody can approve tasks, expenses, KYC
  or commission, or add workers. A launch order question more than a
  bug.

### Medium

**QA-05 Expense amounts with paise show rounded.**
- Steps: log ₹4.55 → Send.
- Expected: ₹4.55. Actual: "EXP-0069 · ₹5" and "Other · ₹5"; month
  totals rounded too. Stored correctly (455 paise).
- Cause: `formatRupees` rounds to whole rupees; amounts entered with
  paise need `formatPaise`.

**QA-06 Over-long note is refused without saying why.**
- Steps: expense note of 250 characters → Send.
- Expected: the field limits to 200, or "Up to 200 characters." under it.
- Actual: banner "Check the fields and try again." only; the server's
  field error (`note: Up to 200 characters.`) isn't shown, and the
  banner stays after the note is fixed.

**QA-07 Any file named `.jpg` is accepted as a receipt or KYC document.**
- Steps: gallery → a text file named `fake-receipt.jpg`.
- Expected: "That isn't a photo" before upload.
- Actual: uploaded and sent (EXP-0069; PAN card "Uploaded"); the
  thumbnail shows "Exception: Invalid image data" (debug) or nothing
  (release). The admin only finds out on opening it.

**QA-08 Sign-up's code screen tells whether an email has an account.**
- Steps: sign up with an existing email → any code.
- Actual: "That code has expired" for an existing account; a new email
  with a wrong code gets "invalid". A script can tell them apart (slowed
  by rate limits). Fix: the same answer for both.

**QA-09 The terms error is hidden behind the submit button.**
- Steps: sign up without ticking the terms.
- Actual: "Tick to agree to continue." sits under the Create account
  button until the page is scrolled. Forms don't scroll to the first
  error.
